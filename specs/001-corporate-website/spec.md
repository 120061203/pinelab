# 功能規格：松果創意 Pinelab 企業官網

**功能分支**: `001-corporate-website`  
**建立日期**: 2025-11-03  
**狀態**: 草稿  
**輸入**: 使用者描述："我需要建立一個企業官網 詳細的內容已經寫在SDD檔案中，請你幫我建立完整的規格檔案"

## 使用者情境與測試 *(必填)*

### 使用者故事 1 - 瀏覽與發現商品 (優先級: P1)

訪客可以透過松果創意企業官網瀏覽和發現商品，透過視覺化的商品展示。首頁顯示品牌形象與最新商品，而專屬的商品頁面讓訪客可以查看所有商品、依分類和標籤篩選、依關鍵字搜尋、依價格區間篩選，並查看詳細商品資訊，包括多張圖片、描述和特點。

**優先級原因**: 這是網站的核心價值主張 - 讓潛在客戶能夠發現並了解松果創意的商品。沒有這個功能，網站就失去了業務目的。

**獨立測試**: 可以透過訪問首頁和商品頁、查看商品列表、套用篩選和存取商品詳情來完整測試。透過向訪客展示商品來提供立即價值。

**驗收情境**:

1. **假設** 訪客進入首頁，**當** 他們查看頁面時，**則** 他們看到松果創意品牌介紹和 6 個最近更新的商品
2. **假設** 訪客導航到商品頁，**當** 他們查看頁面時，**則** 他們看到所有啟用商品的列表，包含圖片、名稱、價格和特點摘要
3. **假設** 訪客在商品頁上，**當** 他們套用分類篩選時，**則** 他們只看到符合該分類的商品
4. **假設** 訪客在商品頁上，**當** 他們套用多個標籤篩選時，**則** 他們看到符合任何所選標籤的商品
5. **假設** 訪客在商品頁上，**當** 他們輸入價格區間（最小和最大）時，**則** 他們只看到該價格區間內的商品
6. **假設** 訪客在商品頁上，**當** 他們輸入關鍵字並點擊搜尋時，**則** 他們看到在名稱、描述或標籤中符合關鍵字的商品
7. **假設** 訪客點擊商品卡片，**當** 他們查看商品詳情頁時，**則** 他們看到完整的商品資訊，包括所有圖片、詳細描述、價格、分類、標籤和突出的特點
8. **假設** 訪客查看商品詳情頁，**當** 他們向下捲動時，**則** 他們看到基於共享分類和標籤推薦的相關商品
9. **假設** 訪客使用行動裝置，**當** 他們查看任何頁面時，**則** 布局適當調整（行動裝置垂直堆疊，較大螢幕響應式網格）

---

### 使用者故事 2 - 聯絡企業 (優先級: P2)

訪客可以透過提交聯絡表單來聯絡松果創意，表單包含姓名、電子郵件地址和訊息。系統驗證輸入、安全儲存提交內容，並立即提供回饋給訪客確認成功提交。

**優先級原因**: 聯絡功能支援潛在客戶開發和客戶詢問，這對業務成長至關重要。雖然次於商品發現，但這是重要的轉換點。

**獨立測試**: 可以透過填寫並提交聯絡表單、驗證驗證規則和確認成功提交來完整測試。透過啟用企業與客戶溝通來提供價值。

**驗收情境**:

1. **假設** 訪客導航到聯絡頁面，**當** 他們查看頁面時，**則** 他們看到包含姓名、電子郵件和訊息欄位的聯絡表單
2. **假設** 訪客在聯絡頁面上，**當** 他們提交包含有效資訊的表單時，**則** 他們看到成功訊息並且表單已提交
3. **假設** 訪客提交聯絡表單，**當** 他們將必填欄位留空時，**則** 他們看到驗證錯誤，指出哪些欄位是必填的
4. **假設** 訪客提交聯絡表單，**當** 他們輸入無效的電子郵件格式時，**則** 他們看到驗證錯誤，指出電子郵件格式不正確
5. **假設** 訪客提交聯絡表單，**當** 他們輸入的訊息短於最小長度時，**則** 他們看到驗證錯誤，指出訊息太短
6. **假設** 訪客使用行動裝置，**當** 他們查看聯絡表單時，**則** 表單以單欄布局顯示，適應螢幕大小

---

### 使用者故事 3 - 管理內容（管理員）(優先級: P3)

授權的管理員可以透過後端 API 管理網站內容，包括建立、讀取、更新和刪除商品、分類和標籤。管理員可以上傳多張商品圖片、調整商品排序，並查看聯絡表單提交內容。API 透過身份驗證和請求簽章來保護。

**優先級原因**: 雖然對網站維護至關重要，但這是較低優先級，因為 MVP 專注於面向公眾的功能。API 可以透過外部工具存取，無需自訂管理介面。

**獨立測試**: 可以透過進行身份驗證的 API 請求來建立、讀取、更新和刪除內容實體來完整測試。透過啟用內容管理而無需自訂管理介面開發來提供價值。

**驗收情境**:

1. **假設** 管理員成功通過身份驗證，**當** 他們透過 API 建立商品時，**則** 商品會儲存所有提供的資訊，包括多張圖片
2. **假設** 管理員建立商品，**當** 他們指定排序順序時，**則** 商品會根據指定的順序顯示
3. **假設** 管理員管理分類，**當** 他們嘗試刪除有關聯商品的分類時，**則** 系統阻止刪除並返回錯誤
4. **假設** 管理員上傳商品圖片，**當** 他們上傳多張圖片時，**則** 所有圖片都會儲存並與商品關聯
5. **假設** 管理員查看聯絡提交內容，**當** 他們透過 API 請求聯絡列表時，**則** 他們收到所有包含時間戳記的聯絡表單提交內容

### 邊緣情況

- 當訪客搜尋不符合任何商品的關鍵字時會發生什麼？（顯示「無結果」訊息並提供建議）
- 系統如何處理沒有指定分類的商品？（顯示無分類，允許依未分類篩選）
- 當商品沒有圖片時會發生什麼？（顯示佔位符圖片或預設圖片）
- 系統如何處理重複的分類或標籤名稱？（防止重複，要求唯一名稱）
- 當聯絡表單提交因網路問題失敗時會發生什麼？（顯示錯誤訊息，允許重試）
- 系統如何處理 URL 中的無效商品 ID？（顯示 404 錯誤頁面並提供有用的訊息）
- 當篩選導致零個商品時會發生什麼？（顯示「沒有商品符合您的篩選條件」訊息，提供清除篩選的選項）
- 當商品沒有共享分類或標籤時，系統如何處理相關商品？（顯示最新商品作為後備）
- 當管理員嘗試在沒有適當身份驗證的情況下存取管理 API 時會發生什麼？（返回 401 未授權錯誤）
- 系統如何處理 min_price 大於 max_price 的價格篩選？（返回驗證錯誤，防止無效範圍）

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系統必須在首頁上顯示松果創意品牌名稱和品牌介紹
- **FR-002**: 系統必須在首頁上顯示最多 6 個最近更新的商品，依更新時間戳記排序
- **FR-003**: 系統必須提供商品列表頁面，顯示所有啟用商品，包含圖片、名稱、價格和特點摘要
- **FR-004**: 系統必須允許訪客依分類篩選商品（單選）
- **FR-005**: 系統必須允許訪客依標籤篩選商品（多選）
- **FR-006**: 系統必須允許訪客依價格區間篩選商品（最小和最大價格）
- **FR-007**: 系統必須允許訪客依關鍵字搜尋商品，在商品名稱、描述和標籤中匹配
- **FR-008**: 系統必須使用「提交後搜尋」模式顯示商品（訪客輸入關鍵字然後點擊搜尋按鈕）
- **FR-009**: 系統必須依手動排序順序顯示商品（指定時）或依更新時間戳記顯示（未指定排序順序時）
- **FR-010**: 系統必須提供商品詳情頁面，顯示完整的商品資訊，包括所有圖片、名稱、價格、分類、標籤、詳細描述和突出的特點
- **FR-011**: 系統必須在商品詳情頁面上顯示相關商品，優先考慮共享分類和標籤
- **FR-012**: 系統必須在沒有相關商品共享分類/標籤時提供後備機制（顯示最新商品）
- **FR-013**: 系統必須提供聯絡表單，包含姓名（必填）、電子郵件（必填，驗證格式）和訊息（必填）欄位
- **FR-014**: 系統必須驗證聯絡表單提交內容，並為無效輸入顯示適當的錯誤訊息
- **FR-015**: 系統必須安全儲存聯絡表單提交內容，並向訪客提供成功確認
- **FR-016**: 系統必須支援響應式網頁設計，為桌面（4 欄網格）、平板（2 欄網格）和行動裝置（1 欄，垂直堆疊）調整布局
- **FR-017**: 系統必須在所有頁面上顯示頁尾，包含品牌名稱和社群媒體連結（Instagram、Facebook、Line@）
- **FR-018**: 系統必須在允許存取內容管理 API 之前驗證管理員身份
- **FR-019**: 系統必須允許管理員透過 API 建立、讀取、更新和刪除商品
- **FR-020**: 系統必須允許管理員透過 API 為每個商品上傳多張圖片
- **FR-021**: 系統必須允許管理員透過 API 調整商品排序順序
- **FR-022**: 系統必須允許管理員透過 API 建立、讀取、更新和刪除分類
- **FR-023**: 系統必須允許管理員透過 API 建立、讀取、更新和刪除標籤
- **FR-024**: 系統必須防止刪除有關聯商品的分類
- **FR-025**: 系統必須允許管理員透過 API 查看聯絡表單提交內容
- **FR-026**: 系統必須透過身份驗證和請求簽章保護所有管理 API 端點
- **FR-027**: 系統必須為商品列表、分類和標籤提供不需要身份驗證的公開 API 端點
- **FR-028**: 系統必須在品牌標誌和詳細聯絡資訊尚未可用時顯示佔位符內容

### 關鍵實體 *(若功能涉及資料，請包含)*

- **商品**: 代表松果創意提供的商品。關鍵屬性包括名稱、描述、價格、分類關聯、標籤關聯、多張圖片、排序順序和啟用狀態。商品可以被篩選、搜尋和排序。每個商品屬於一個分類（一對多關係），可以有多個標籤（多對多關係）。

- **分類**: 代表由管理員管理的商品分類。關鍵屬性包括名稱和排序順序。分類用於組織和篩選商品。如果分類有關聯商品，則無法刪除。

- **標籤**: 代表由管理員管理的商品標籤。關鍵屬性包括名稱。標籤用於靈活的商品標記和篩選。多個標籤可以與商品關聯（多對多關係）。

- **聯絡提交**: 代表訪客的聯絡表單提交內容。關鍵屬性包括訪客姓名、電子郵件地址、訊息內容和提交時間戳記。用於潛在客戶開發和客戶詢問。

- **商品圖片**: 代表與商品關聯的圖片。關鍵屬性包括圖片檔案、排序順序和主圖標記。多張圖片可以與每個商品關聯（一對多關係）。

- **管理員**: 代表可以透過 API 管理網站內容的授權使用者。關鍵屬性包括身份驗證憑證和權限。管理員透過身份驗證的 API 端點存取內容管理功能。

## 成功標準 *(必填)*

### 可測量結果

- **SC-001**: 訪客可以在標準寬頻連線下，在 3 秒內完成查看首頁並識別 6 個最新商品
- **SC-002**: 訪客可以在 10 秒內導航到商品頁、套用篩選並找到相關商品
- **SC-003**: 訪客使用有效資訊時，95% 的情況下可以在第一次嘗試時成功提交聯絡表單
- **SC-004**: 所有頁面在行動裝置（螢幕寬度從 320px 到 768px）和桌面裝置（螢幕寬度從 1024px 到 2560px）上都能正確載入和顯示
- **SC-005**: 商品搜尋在 2 秒內為關鍵字查詢返回相關結果
- **SC-006**: 商品篩選（分類、標籤、價格）在 1 秒內返回篩選結果
- **SC-007**: 商品詳情頁面 100% 正確顯示所有關聯的圖片和資訊
- **SC-008**: 相關商品區段在可用時顯示至少 3 個相關商品建議（具有共享分類或標籤的商品）
- **SC-009**: 管理員可以在 5 秒內透過 API 建立包含圖片的新商品
- **SC-010**: 聯絡表單提交內容在提交後 1 分鐘內成功儲存並可被管理員存取
- **SC-011**: 網站支援至少 100 個訪客同時存取不同頁面而不會降低性能
- **SC-012**: 所有面向公眾的頁面無需身份驗證即可存取，所有管理功能都需要適當的身份驗證

## 假設

- 品牌標誌和詳細聯絡資訊將在稍後提供；佔位符內容對 MVP 來說是可以接受的
- 商品目錄將從大約 2 個商品開始，因此重點應該放在商品特點呈現上，而不是大規模目錄管理
- MVP 階段不需要 AI 驅動的推薦功能
- MVP 階段不需要自訂管理員前端介面；API 存取就足夠了
- 公開商品列表不需要身份驗證或請求簽章
- 聯絡表單提交內容需要請求簽章以確保安全，但不需要使用者身份驗證
- 圖片儲存使用本地檔案系統；雲端儲存可以稍後實作
- 商品圖片沒有嚴格的數量限制，但建議每個商品實用限制為 10 張圖片
- 社群媒體連結最初可以使用佔位符 URL，稍後更新為實際 URL
- 網站將使用容器化基礎設施部署
- 將為前端和後端元件實作自動化測試

## 依賴項

- 內容管理系統（後端 API）必須在面向公眾的頁面可以顯示動態商品資料之前可用
- 商品圖片必須在上傳和儲存後，商品詳情頁面才能顯示完整資訊
- 管理員帳戶必須在可以使用內容管理功能之前建立和配置
- 品牌資產（標誌、品牌顏色、字體）應提供給一致的品牌呈現（對 MVP 來說是可選的）

## 不在範圍內

- 訪客的使用者註冊和登入功能（MVP 中不需要）
- 購物車和結帳功能（明確排除在需求之外）
- 支付處理整合（明確排除在需求之外）
- AI 驅動的商品推薦服務（延後到未來階段）
- 自訂管理員前端介面（MVP 的 API 存取就足夠了）
- 訂單管理功能（明確排除在需求之外）
- 即時通知或聊天功能
- 訪客的使用者帳戶和個人資料
- 商品評論或評分系統
- 聯絡表單提交的電子郵件通知（假設手動後續處理）
