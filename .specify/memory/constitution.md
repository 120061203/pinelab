# Pinelab Constitution

## Core Principles

### I. 程式品質 (Code Quality) - NON-NEGOTIABLE

所有程式碼必須遵循高品質標準，確保可維護性、可讀性和可擴展性。

**要求**:
- 模組化設計：每個模組只負責單一領域（SRP 原則），可獨立開發、部署與測試
- 程式碼審查：所有程式碼變更必須經過 peer review，未通過審查不得合併
- 程式碼風格：遵循語言與框架的官方風格指南（Python PEP 8, TypeScript ESLint 規則）
- 靜態分析：所有程式碼必須通過 linter 檢查，無重大警告或錯誤
- 複雜度控制：函數/方法圈複雜度不超過 10，單一檔案行數不超過 500 行
- 文件完整性：所有公開 API、類別和方法必須包含文件字串或註解

**理由**: 高品質程式碼降低維護成本，提升團隊協作效率，減少技術債務累積。

---

### II. 測試標準 (Testing Standards) - NON-NEGOTIABLE

測試優先開發（Test-First Development），確保功能正確性和回歸防護。

**要求**:
- TDD 流程：測試先寫（Red）→ 實作功能（Green）→ 重構（Refactor），嚴格執行
- 測試覆蓋率：單元測試覆蓋率必須達到 80% 以上，關鍵業務邏輯達到 90% 以上
- 測試分類：單元測試（模型、服務、工具函數）、整合測試（API 端點、資料庫操作）、端到端測試（使用者流程）
- 測試獨立性：所有測試必須可獨立執行，不依賴外部服務或特定執行順序
- 測試自動化：所有測試必須在 CI/CD pipeline 中自動執行，測試失敗阻擋部署
- 測試可讀性：測試名稱清楚描述測試情境，使用 Given-When-Then 結構

**理由**: 完整的測試套件提供安全網，支援重構和快速迭代，確保功能穩定性。

---

### III. 使用者體驗一致性 (User Experience Consistency)

確保所有使用者介面與互動體驗保持一致性和可預測性。

**要求**:
- 設計系統：遵循統一的設計系統（顏色、字體、間距、元件樣式）
- 響應式設計：所有頁面必須在桌面（≥1024px）、平板（768-1023px）、手機（320-767px）上正常顯示
- 互動一致性：相同操作在不同頁面應有相同的行為和回饋
- 錯誤處理：所有錯誤訊息必須友善、明確，並提供可行的解決建議
- 載入狀態：所有非同步操作必須顯示明確的載入狀態指示
- 無障礙設計：符合 WCAG 2.1 AA 等級標準，支援鍵盤導航和螢幕閱讀器

**理由**: 一致的體驗降低使用者學習成本，提升品牌專業形象，改善使用者滿意度。

---

### IV. 效能需求 (Performance Requirements)

系統必須滿足既定的效能目標，確保良好的使用者體驗。

**要求**:
- 回應時間：API 端點回應時間必須符合規格要求（商品列表 < 1 秒，搜尋 < 2 秒，首頁載入 < 3 秒）
- 並發能力：系統必須支援至少 100 個並發使用者而不降低效能
- 資源優化：前端資源（圖片、CSS、JS）必須經過壓縮和優化，減少載入時間
- 資料庫效能：所有查詢必須使用適當索引，避免 N+1 查詢問題，慢查詢必須優化
- 快取策略：合理使用快取機制（瀏覽器快取、API 回應快取）減少伺服器負載
- 效能監控：實作效能監控和日誌記錄，追蹤關鍵指標（回應時間、錯誤率、吞吐量）

**理由**: 良好的效能直接影響使用者體驗和業務轉換率，是企業網站成功的重要因素。

## Quality Standards

### 程式碼品質指標

- **Linter 檢查**: 零錯誤，警告數量最小化（< 5 個可接受的警告）
- **型別檢查**: TypeScript/Python 型別檢查 100% 通過
- **程式碼覆蓋率**: 單元測試覆蓋率 ≥ 80%，整合測試覆蓋關鍵流程
- **程式碼審查**: 所有 PR 必須經過至少 1 位團隊成員審查
- **技術債務追蹤**: 記錄並優先處理技術債務項目

### 測試品質指標

- **測試穩定性**: 測試套件穩定性 ≥ 95%（無間歇性失敗）
- **測試執行時間**: 單元測試套件執行時間 < 5 分鐘，整合測試 < 15 分鐘
- **測試維護性**: 測試程式碼必須與業務程式碼同等品質標準
- **測試文件**: 複雜測試必須包含說明文件，解釋測試目的和情境

### 使用者體驗指標

- **頁面載入速度**: 首屏內容載入（FCP）< 2 秒，完整頁面載入（LCP）< 3 秒
- **互動回應**: 使用者操作回應時間 < 100ms（按鈕點擊、表單提交等）
- **錯誤率**: 使用者可見錯誤率 < 1%
- **跨瀏覽器相容性**: 支援最新 2 個版本的 Chrome、Firefox、Safari、Edge

### 效能指標

- **API 回應時間**:
  - P50（中位數）< 200ms
  - P95（95 百分位）< 500ms
  - P99（99 百分位）< 1 秒
- **系統吞吐量**: 支援 100+ 並發使用者無效能降級
- **資源使用**: 記憶體使用穩定，無記憶體洩漏；CPU 使用率正常範圍
- **資料庫效能**: 查詢時間 < 100ms（複雜查詢可放寬至 500ms）

## Development Workflow & Quality Gates

### 開發流程

1. **功能開發前**:
   - 確認功能規格已通過審查
   - 確認技術設計符合 Constitution 原則
   - 建立功能分支並設定 CI/CD

2. **開發過程中**:
   - 遵循 TDD 流程：先寫測試，確保測試失敗，再實作功能
   - 定期執行 linter 和型別檢查
   - 頻繁提交小幅度變更（每個任務或邏輯群組）

3. **提交前**:
   - 所有測試必須通過
   - Linter 檢查必須通過（零錯誤）
   - 型別檢查必須通過
   - 程式碼覆蓋率必須達標

4. **Code Review**:
   - 至少 1 位團隊成員審查
   - 審查重點：程式品質、測試完整性、效能影響、UX 一致性
   - 必須解決所有審查意見才能合併

5. **合併後**:
   - CI/CD pipeline 自動執行完整測試套件
   - 自動部署到測試環境（如適用）
   - 效能回歸檢查（如適用）

### Quality Gates

所有功能必須通過以下檢查點才能合併：

1. ✅ **程式碼品質 Gate**: Linter 檢查通過，型別檢查通過，程式碼審查通過
2. ✅ **測試 Gate**: 所有測試通過，測試覆蓋率達標，無測試退步
3. ✅ **效能 Gate**: 效能指標符合要求，無效能回歸
4. ✅ **UX Gate**: 設計審查通過（如適用），響應式設計驗證通過
5. ✅ **文件 Gate**: 公開 API 文件完整，重要變更有說明文件

### 例外處理

違反 Constitution 原則的決策必須：
- 在 PR 描述中明確說明理由
- 取得技術負責人批准
- 記錄在 Complexity Tracking 文件中
- 制定後續改進計畫

## Governance

### Constitution 優先級

Constitution 原則超越所有其他實務規範。任何與 Constitution 衝突的實務必須：
- 修正實務以符合 Constitution
- 或透過 Governance 流程修改 Constitution

### 修正流程

1. **提案**: 提出 Constitution 修正提案，說明原因和影響
2. **討論**: 團隊討論並評估修正影響
3. **批准**: 需要技術負責人或團隊共識批准
4. **文件化**: 記錄修正內容、理由和版本變更
5. **遷移**: 如有破壞性變更，必須制定遷移計畫

### 版本控制

- **MAJOR**: 原則移除或重新定義、破壞性變更
- **MINOR**: 新增原則或章節、大幅擴充指引
- **PATCH**: 澄清說明、措辭修正、非語義性改進

### 合規檢查

- **PR 審查**: 所有 PR 必須驗證符合 Constitution 原則
- **定期審查**: 每季度審查 Constitution 與實際執行情況的一致性
- **工具支援**: 使用自動化工具檢查程式品質和測試覆蓋率

### 複雜度追蹤

任何增加系統複雜度的決策必須在 `plan.md` 的 Complexity Tracking 章節中記錄：
- 違反的原則
- 需要的理由
- 拒絕的簡單替代方案及其原因
